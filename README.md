# WildfireSimulator

Программный комплекс для имитационного моделирования, визуализации и анализа распространения лесных пожаров.

Проект разработан в рамках выпускной квалификационной работы:

> «Разработка имитационной модели распространения лесных пожаров с использованием графовых алгоритмов и потоковой обработки данных».

WildfireSimulator объединяет вычислительную модель распространения пожара, ASP.NET Core Web API, хранение и восстановление состояния в PostgreSQL, потоковую обработку метрик через Apache Kafka и кроссплатформенное desktop-приложение на Avalonia UI.

Система позволяет создать модель лесного массива, задать параметры окружающей среды, выбрать очаги возгорания, управлять выполнением симуляции и наблюдать за изменением территории и аналитических показателей в реальном времени.

> Проект является исследовательской имитационной системой и не предназначен для прогнозирования или принятия решений при реальных лесных пожарах.

## О проекте

WildfireSimulator — полноценное клиент-серверное приложение, состоящее из нескольких взаимосвязанных частей:

- вычислительной модели распространения пожара;
- генератора сеточных и графовых моделей территории;
- серверного REST API;
- базы данных с сохранением истории и состояния симуляций;
- системы передачи и потоковой обработки событий;
- механизма обновления клиента в реальном времени;
- desktop-интерфейса для управления и визуализации;
- тестовых и экспериментальных сценариев;
- shell-скриптов для запуска и проверки компонентов.

Основная задача проекта — исследовать, как параметры территории и окружающей среды влияют на развитие пожара в дискретной модели лесного массива.

## Что реализовано

### Сеточная и графовая модели территории

Поддерживаются два способа представления лесного массива:

- регулярная двумерная сетка;
- графовая модель территории.

В сеточной модели участки связаны с соседними клетками по горизонтали и вертикали.

В графовой модели:

- вершина представляет отдельный участок территории;
- ребро определяет возможность передачи теплового воздействия;
- параметры ребра учитывают расстояние и уклон;
- поддерживаются кластерные структуры;
- используются связи между отдельными областями графа;
- параметры связей влияют на распространение огня.

Для каждого участка территории хранятся:

- координаты;
- высота;
- тип растительности;
- влажность;
- запас горючего материала;
- текущее состояние;
- время горения;
- накопленное тепло;
- порог воспламенения.

Основные состояния участка:

- нормальный;
- горящий;
- выгоревший.

В модели также используются вода и участки без растительности. Они выступают естественными препятствиями и снижают или полностью останавливают передачу тепла.

### Генерация территории

Система автоматически формирует исходную модель лесного массива.

При генерации задаются:

- размеры территории;
- тип структуры;
- распределение растительности;
- диапазон начальной влажности;
- перепад высот;
- плотность горючего материала;
- количество начальных очагов;
- случайное зерно генерации.

Генератор может создавать:

- регулярную сетку;
- кластерные графовые структуры;
- участки с разной растительностью;
- водные объекты;
- открытые участки без растительности;
- неоднородный рельеф;
- области с различной влажностью.

После генерации пользователь может просмотреть подготовленную модель и отредактировать отдельные участки до запуска симуляции.

### Вычислительная модель пожара

Распространение пожара выполняется пошагово.

На каждом шаге система:

1. определяет активные горящие участки;
2. рассчитывает интенсивность горения;
3. находит связанные с ними участки;
4. рассчитывает тепловой поток;
5. учитывает расстояние между участками;
6. учитывает направление и скорость ветра;
7. учитывает уклон местности;
8. применяет влияние влажности и осадков;
9. накапливает полученное участком тепло;
10. рассчитывает порог воспламенения;
11. определяет вероятность нового возгорания;
12. уменьшает запас топлива горящих участков;
13. переводит полностью выгоревшие участки в новое состояние;
14. охлаждает участки, которые не воспламенились;
15. формирует результаты и метрики шага.

Вычислительная модель учитывает:

- тип растительности;
- количество топлива;
- влажность участка;
- температуру воздуха;
- влажность воздуха;
- скорость ветра;
- направление ветра;
- интенсивность осадков;
- расстояние;
- уклон;
- стадию горения;
- количество источников теплового воздействия.

Один пользовательский шаг может разделяться на несколько внутренних подшагов. Это позволяет более последовательно обновлять состояние модели при большой длительности шага.

### Управление симуляциями

Пользователь может:

- создать новую симуляцию;
- выбрать сеточную или графовую модель;
- задать параметры территории;
- настроить погодные условия;
- указать длительность и количество шагов;
- выбрать случайные очаги возгорания;
- выбрать очаги вручную;
- редактировать подготовленную карту;
- запустить симуляцию;
- выполнить один шаг;
- включить автоматический режим;
- приостановить автоматическое выполнение;
- остановить симуляцию;
- сбросить состояние;
- повторно запустить модель;
- удалить симуляцию;
- получить текущее состояние;
- просмотреть историю метрик.

### Серверный API

Серверная часть реализована на ASP.NET Core Web API.

API отвечает за:

- создание симуляций;
- получение списка симуляций;
- получение информации по идентификатору;
- удаление симуляций;
- запуск моделирования;
- выполнение одного шага;
- остановку;
- сброс состояния;
- получение текущего статуса;
- получение полной структуры территории;
- обновление стартовых очагов;
- предварительную генерацию графовой модели;
- получение истории метрик.

В серверной части также реализованы:

- Dependency Injection;
- DTO для обмена данными;
- централизованная обработка исключений;
- единообразные ответы об ошибках;
- журналирование HTTP-запросов;
- измерение времени выполнения запросов;
- идентификаторы трассировки;
- endpoint проверки состояния приложения.

### Хранение и восстановление состояния

Для хранения данных используется PostgreSQL и Entity Framework Core.

В базе данных сохраняются:

- параметры симуляции;
- погодные условия;
- тип территории;
- структура сетки или графа;
- вершины и связи;
- состояния участков;
- выбранные очаги возгорания;
- номер текущего шага;
- состояние активной симуляции;
- результаты выполненных шагов;
- история метрик.

Сложные структуры сохраняются в сериализованном виде с использованием полей PostgreSQL `JSONB`.

Для доступа к данным применяются репозитории, которые отделяют прикладную логику от конкретного механизма хранения.

Состояние активной симуляции может быть восстановлено после перезапуска серверного приложения. Восстанавливаются:

- параметры модели;
- структура территории;
- погодные условия;
- текущий шаг;
- состояние участков;
- агрегированные показатели.

### Потоковая обработка данных

После выполнения шага события и метрики публикуются в Apache Kafka.

Фоновые сервисы получают сообщения и выполняют потоковый анализ.

Рассчитываются:

- площадь пожара;
- количество горящих участков;
- количество выгоревших участков;
- скорость изменения площади;
- ускорение распространения;
- скользящее среднее `SMA3`;
- скользящее среднее `SMA5`;
- скользящее среднее `SMA10`;
- аномальные изменения показателей;
- краткосрочный прогноз площади;
- средняя абсолютная ошибка прогноза `MAE`.

Для прогнозирования используется линейная регрессия по накопленной истории метрик.

Kafka используется для отделения вычислительной части симуляции от последующего анализа и доставки результатов клиенту.

### Обновления через SignalR

Результаты потоковой обработки передаются в SignalR Hub.

Клиент подписывается на конкретную симуляцию и получает только связанные с ней данные.

В реальном времени передаются:

- изменения метрик;
- скользящие средние;
- динамика распространения;
- прогнозы;
- информация об аномалиях;
- состояние подключения.

SignalR позволяет обновлять клиент без постоянного опроса API.

### Desktop-приложение

Клиентская часть разработана на Avalonia UI с использованием XAML и MVVM.

Приложение предоставляет единое рабочее пространство для создания, запуска, визуализации и анализа симуляций.

Клиент позволяет:

- указывать адрес API;
- проверять соединение с сервером;
- просматривать список симуляций;
- создавать и удалять симуляции;
- переключаться между сеткой и графом;
- редактировать подготовленную территорию;
- выбирать очаги возгорания;
- запускать и останавливать моделирование;
- выполнять отдельные шаги;
- использовать автоматический режим;
- наблюдать изменение состояния участков;
- просматривать параметры среды;
- отображать текущие метрики;
- загружать историю показателей;
- получать потоковые данные через SignalR;
- просматривать прогнозы и обнаруженные аномалии;
- вести журнал событий интерфейса.

MVVM используется для разделения представления и логики клиента. Команды, состояние интерфейса и асинхронное взаимодействие с сервером находятся в моделях представления.

## Архитектура

Проект построен на основе многоуровневой архитектуры.

### Domain

Содержит предметные модели:

- лесной граф;
- участки территории;
- связи между участками;
- погодные условия;
- параметры симуляции;
- состояние активной симуляции;
- метрики пожара.

Domain не зависит от пользовательского интерфейса, API и базы данных.

### Application

Содержит прикладную и вычислительную логику:

- расчет теплового воздействия;
- расчет интенсивности горения;
- выполнение шага;
- управление симуляциями;
- формирование событий;
- расчет метрик;
- контракты сервисов;
- контракты репозиториев;
- DTO.

### Infrastructure

Содержит взаимодействие с внешними системами:

- Entity Framework Core;
- PostgreSQL;
- миграции;
- реализации репозиториев;
- генерацию территории;
- Kafka producer;
- Kafka consumer;
- фоновые сервисы обработки сообщений;
- конфигурацию инфраструктурных компонентов.

### API

Предоставляет REST API, управляет входящими запросами и передает команды прикладному уровню.

Также API содержит SignalR Hub, middleware обработки ошибок, логирование и endpoint проверки состояния.

### Client

Кроссплатформенное Avalonia-приложение, взаимодействующее с сервером через HTTP API и SignalR.

Основной поток данных:

```text
Avalonia Client
      │
      ├── HTTP/REST ──> ASP.NET Core API
      │                       │
      │                       ├── Application
      │                       │       │
      │                       │       └── Domain
      │                       │
      │                       └── Infrastructure ──> PostgreSQL
      │
      └── SignalR <── SignalR Hub <── Kafka consumer
                                           │
                                           └── Apache Kafka
                                                  │
                                                  └── события и метрики симуляции
```

## Как работает система

### 1. Создание модели

Пользователь задает параметры симуляции в desktop-приложении.

Клиент отправляет запрос в ASP.NET Core API.

### 2. Формирование территории

Сервер создает сеточную или графовую структуру и назначает каждому участку начальные параметры:

- растительность;
- влажность;
- высоту;
- запас топлива;
- состояние.

### 3. Настройка очагов

Начальные очаги выбираются случайно или указываются пользователем вручную.

До запуска можно изменить отдельные элементы подготовленной территории.

### 4. Выполнение шага

Вычислительный сервис рассчитывает тепловое воздействие и обновляет состояние каждого участка.

После завершения шага формируются агрегированные показатели пожара.

### 5. Сохранение данных

Состояние территории, текущий шаг и метрики сохраняются в PostgreSQL.

### 6. Публикация событий

Результаты шага публикуются в Apache Kafka.

Фоновые сервисы рассчитывают дополнительные показатели и прогнозы.

### 7. Обновление клиента

Обработанные данные поступают в SignalR Hub.

Клиент получает обновления и изменяет визуализацию, метрики и аналитические показатели.

## Основные API endpoints

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/simulations` | Получить список симуляций |
| `GET` | `/api/simulations/{id}` | Получить симуляцию |
| `POST` | `/api/simulations` | Создать симуляцию |
| `DELETE` | `/api/simulations/{id}` | Удалить симуляцию |
| `POST` | `/api/SimulationManager/{id}/start` | Запустить симуляцию |
| `POST` | `/api/SimulationManager/{id}/step` | Выполнить один шаг |
| `POST` | `/api/SimulationManager/{id}/stop` | Остановить выполнение |
| `POST` | `/api/SimulationManager/{id}/reset` | Сбросить состояние |
| `GET` | `/api/SimulationManager/{id}/status` | Получить текущий статус |
| `GET` | `/api/SimulationManager/{id}/graph` | Получить структуру территории |
| `POST` | `/api/SimulationManager/{id}/refresh-ignitions` | Обновить стартовые очаги |
| `POST` | `/api/SimulationManager/preview-clustered-blueprint` | Подготовить граф для редактора |
| `GET` | `/health` | Проверить состояние API |

## Запуск

### Запуск через shell-скрипт

Основной вариант запуска автоматизирован shell-скриптом, расположенным в репозитории (start_full_system.sh).

Скрипт используется для последовательного запуска необходимых компонентов системы.

### Ручной запуск

#### Инфраструктура

```bash
docker compose up -d
```

Docker Compose запускает:

- PostgreSQL;
- ZooKeeper;
- Apache Kafka.

Проверка контейнеров:

```bash
docker compose ps
```

#### API

```bash
dotnet run --project WildfireSimulator.API
```

Проверка состояния:

```text
http://localhost:5198/health
```

#### Desktop-клиент

```bash
dotnet run --project WildfireSimulator.Client
```

По умолчанию клиент использует адрес:

```text
http://localhost:5198
```

### Остановка инфраструктуры

```bash
docker compose down
```

Удаление контейнеров и сохраненных томов:

```bash
docker compose down -v
```

## Ограничения

- Модель является исследовательской и использует дискретное представление территории.
- Значения коэффициентов настроены для демонстрации и исследования поведения модели.
- Результаты не являются метеорологическим прогнозом.
- Система не использует реальные спутниковые или картографические данные.
- Прогноз площади основан на истории текущей симуляции и линейной регрессии.
- Тестовые сценарии не означают полное промышленное покрытие проекта автоматическими тестами.
